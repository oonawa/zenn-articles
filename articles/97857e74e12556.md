現在、Next.jsでフルスタックなアプリケーションを開発しています。ご多分に漏れずClaude Codeを活用して実装しています。

AIとの協業においても、自動テストは重要です。テストコードの実装とはプロダクトコードの設計作業でもあり、動作する要件定義書の作成でもあるためです。Gitフローに組み込んでおけば、既存の要件を満たさないコードがデプロイされる可能性を強制的に減らすこともできます。

極端に言えばプロダクトコードが動かないことよりも、テストコードが動かないことの方が問題だとさえ思っています。手動の動作確認よりも確実で高速な自動テストさえあれば、「このテストをグリーンにする」という方向へ実装の方針をきっちり定めることができるためです。「テストをグリーンにする」という指標は、ほとんどの場合で自然言語のプロンプトよりも機械的で確実です。

## フロントエンドのテストはどうしたらいい？

個人的な経験則として、Server Actionsで構成しているサーバーサイドはVitestでシンプルにテストを書ける認識がありました。

しかし問題となったのがフロントエンドのテストです。私にはReactアプリケーションのUIを検証する自動テストを実装した経験が全くありませんでした。

調査した結果、2026年現在は仮想ブラウザベースのテスティングフレームワークが最適と判断しました。そこで採用したのがPlaywrightです。

JAMstackでのWeb制作の一環としてシンプルなVRTだけは実装した経験があったのですが、本格的なUIに対するテストは初めてです。ほとんどバイブコーディングのような形で、Claude主体での実装を行いました。

## なぜPlaywrightだったのか

### テスト戦略との適合

テストサイズという概念があります。

自動テストの分類手法であり、スコープというよりは実行範囲で定義しているものです。
こちらの記事でわかりやすく説明されています。
https://gihyo.jp/dev/serial/01/savanna-letter/0003

定義としては以下のとおりです。

| サイズ | 定義 |
| — | — | 
| Small | 単一プロセスで実行 |
| Medium | 単一マシンで実行 | 
| Large | 外部API等も含め制限なし |

今回は以下の理由からMediumサイズを主軸に据えて実装しています。

- 自動テストがないプロダクトに後から実装する上で最適なサイズであること。
- 設計変更やリファクタリングがしやすいこと。

例えばバックエンドでは、Server Actionsを入口として最終的な戻り値＋データベースの状態を検証するテストを書いています。

テストにこの程度のスコープを持たせておけば、同じ入力に対する最終的な結果が変わらないことを常に確認しながら設計変更・リファクタリングを進めることができます。内部品質の改善が必要なレガシーシステムや、構造が変化し続けることが予想される新規プロダクトによく適合するのがMediumサイズです。

すでにこのようなテスト環境が整えられていたので、仮想ブラウザを使用したE2Eテストもスムーズに導入できると考えました。

### 実際のブラウザでテストできる

Playwrightは、実際のブラウザエンジンでレンダリングをした上でアプリケーションを動かすことができます。

ReactフロントエンドをテストするツールとしてはReact Testing Library（RTL）の存在も知っていましたが、RTLはブラウザAPIの代替実装である`jsdom`を実行基盤とします。
実際のブラウザとは環境差異が生じる懸念があり、特にReactの`useOptimistic`等のモダンなAPIを使用したUIが動作するか不安でした。

さらに今回は新規開発であるため、しばらくは機能追加・仕様変更・スタイル修正が活発に行われることが前提です。

コンポーネント単位などの詳細に踏み込んだテストには`jsdom`ベースのライブラリも適合するかもしれませんが、少しの変更で通らなくなるテストを増やしてもUI変更のコストが上がるばかりでメリットは多くありません。

Mediumテストを中心とする戦略もあり、アプリケーションの細部よりは動作（ふるまい）を広範的にテストできる手法の方が望ましいと考えPlaywrightの採用に至りました。

### Vitest Browser Modeの検討

Vitest Browser Modeについては、選定の段階では明確に調査・比較していませんでした。存在を知った1年以上前は実験的な機能であり、まだ導入できる段階ではないという印象のまま忘れていたからです。

ただ現時点で改めて調査してみると、Browser ModeはE2Eテストよりはコンポーネント単体を実ブラウザで動作させるテストに特化しているようでした。今回はページごとをスコープとして「機能」という大きな単位をテストしたかったため、いずれにしてもPlaywrightの方が要件にマッチしていると考えています。

後ほど紹介しますが、Playwrightを使ってChromiumでのスロットリングによるパフォーマンス要件のテストなども実装しています。そういった非機能要件のテストも書けるところも便利だと感じています。

## やったこと

### DBを使う機能のテスト

仮想ブラウザの操作からデータベースへの書き込みまでを通したE2Eテストです。Vitestで書いていたサーバーサイドのMediumテストと同じく、テスト前にシーディング、テスト後にクリーンアップという流れで組んでいます。

DBへの参照は、Drizzle ORMのクライアントをE2Eテスト用に切り出した薄いラッパーを介して行います。アプリ側のクライアントは`top-level await`を含む都合でPlaywrightから直接importできなかったため、`tests/e2e/lib/testDb.ts`に別途用意しました。

Playwrightの`globalSetup`では、初回のみマイグレーションとマスターデータの投入を行います。

```ts:tests/e2e/globalSetup.ts
export default async function globalSetup() {
    await db.run(sql`PRAGMA journal_mode=WAL`);
    await migrate(db, { migrationsFolder: "./migrations" });
    await seedDatabase();
}
```

各テストファイルでは`beforeEach`でテーブルをクリーンアップ＋マスターデータを再投入し、`afterEach`でもう一度クリーンアップしています。これでテスト間の独立性を保ち、実行順序に依存しないようにしています。

```ts
test.describe("MovieInputForm - 機能テスト", () => {
    test.beforeEach(async () => {
        await resetDatabase();
        await seedDatabase();
    });

    test.afterEach(async () => {
        await resetDatabase();
    });

    test("...", async ({ page }) => {
        // ページ操作とアサーション
    });
});
```

テスト本体は、ブラウザ操作（フォーム入力やボタンクリック）と、それによって発生するDB側の状態変化の両方をアサーションの対象にします。サーバーサイドのテストと同じく「同じ入力なら同じ最終状態に至ること」を担保する構成です。

### LocalStorageを使う機能のテスト

今回のアプリには、アカウントを持たないゲストユーザー向けの仕様があります。

未ログイン状態ではデータをサーバーに保存せず、ブラウザのLocalStorageへ永続化することで、登録不要でアプリを試せるようにしています。Jotaiの`atomWithStorage`を使い、LocalStorageとReact側のステートを同期する構成です。

このようなLocalStorage依存の機能をE2Eテストする際は、ページにアクセスするより前にLocalStorageへ値を入れておきたくなります。このようなシーディングにはPlaywrightの`addInitScript`を使用しました。

https://playwright.dev/docs/api/class-page#page-add-init-script

このAPIではページのJavaScriptが評価されるよりも前に任意のスクリプトを実行できるため、ページアクセス時点ですでにデータが存在する状態を作れます。

```ts
await page.addInitScript((data) => {
    localStorage.setItem("key", JSON.stringify(data));
}, seedData);

await page.goto("/");
```

### 外部サービスに依存した機能のテスト

参考にした講演：https://www.youtube.com/watch?v=C0zNc4bdWhY

今回のアプリケーションでは、パスワードレス認証のために6桁のログインコードをメール送信する機能があり、メール送信には[Resend](https://resend.com/)を使っています。

E2Eテストで悩むのが、外部のSaaSや課金枠を消費するサービスに依存した機能の扱いです。実物のサービスへリクエストを飛ばす場合はスコープがネットワーク外部へ及ぶため、テストサイズで表すと「Large」になります。

Largeテストには次のような問題があります。

- 外部サービスのレート制限・ネットワーク状況に左右されて実行が安定しない
- 通信のオーバーヘッドがあるため実行時間が長い

これらの問題を解消するためには、テストサイズをLargeからMediumに下げるのが効果的です。

テストサイズは依存対象をモックへ差し替えることで下げることができます。今回はResendを置き換えるフェイク実装として[`resend-local`](https://www.npmjs.com/package/resend-local)というOSSを採用しました。Resendと同じAPI仕様を持つローカルサーバーです。

Playwrightの`webServer`で、Next.jsの起動と並行して`resend-local`を立ち上げています。

```ts:playwright.config.ts
webServer: [
    {
        command: "npx resend-local --port 8005",
        url: "http://localhost:8005",
        reuseExistingServer: !process.env.CI,
    },
    {
        command: "npx dotenv-cli -e .env.test -- npm run start -- -p 3001",
        // ...
    },
],
```

テスト側では、`resend-local`が提供するREST APIをポーリングして送信済みメールを取得し、本文から6桁のコードを抜き出してログインフォームへ入力する、というヘルパーを書いています。

```ts:tests/e2e/helpers/resendLocal.ts
export async function extractLoginCode(toEmail: string): Promise<string> {
    // resend-local のメール一覧APIをポーリングして
    // 宛先メールアドレスに一致する最新メールから6桁コードを抽出する
}
```

### パフォーマンスのテスト

Playwrightは、Chromium DevTools Protocol（CDP）を介してネットワークスロットリングを設定できます。これを使うと、低速ネットワーク下での読み込み速度やUIの反応速度を、機能テストと同じ仕組みの中で検証できます。

今回のアプリでは、3G相当のネットワーク条件をエミュレートしたうえで「初期表示で優先したい要素が一定時間内に表示される」「ユーザー操作に対してUIが即座にフィードバックを返す」といった項目をテストしています。

```ts
const THROTTLING_3G = {
    offline: false,
    downloadThroughput: 750_000,
    uploadThroughput: 250_000,
    latency: 100,
} as const;

const cdpSession = await context.newCDPSession(page);
await cdpSession.send("Network.emulateNetworkConditions", THROTTLING_3G);
await page.goto("/", { waitUntil: "domcontentloaded" });
await expect(page.locator('textarea[name="value"]')).toBeVisible({
    timeout: 2000,
});
```

このようなテストを書くと、コードベース上で「初期表示において、どの要素を最優先で見せるべきか」が言語化された状態で残ります。新たにコンポーネントを追加するときも、この優先度を踏まえて読み込みタイミングや遅延ロードの方針を決められるようになり、UI設計の指針として機能します。

## トラブル

### LocalStorageを使う機能のテストがフレイキー

今回のアプリケーションでは、ユーザーはアカウント登録をしなくてもLocalStorageへデータを永続化することができます。そのようなゲストユーザーのテストケースにおいて、データ操作を行うテストが成功したり失敗したりする**フレイキーテスト**になりました。

問題の根本原因は初期データの投入です。最初は以下のような実装になっていました。

```ts
await page.goto("/");

await page.evaluate(() => {
	localStorage.setItem("key", JSON.stringify(seedData));
});

await page.reload();
```

ページへアクセスし、LocalStorageへデータをセットして一度リロードするという方法です。初回アクセス時はデータが空ですが、リロード後は一覧画面が表示されるようになります。

テストが成功することもあるのですが、失敗する場合は画面上にデータが表示されておらず、存在しない要素を操作しようとしてタイムアウトで落ちていました。

まず、テストのためにリロードをはさんでいること自体が不自然でした。リロードの完了からハイドレーションに至るまでの処理時間はまちまちであり、これそのものが不安定要素になります。

さらに今回はJotaiの`atomWithStorage`を使用しており、LocalStorageとステートを同期させています。こうなるとハイドレーション後にステートの初期化も加わるため、操作可能になるタイミングがさらに遅延することになります。

今回のアプリの仕様として、リストIDという値を必要としていました。

- 一覧画面で表示する各データは「リスト」に属している
- リストは固有のIDを持つ

LocalStorageで永続化する際には以下のような構造でデータを持ちます。

```json
{
    listId: "リストID",
    items: [
    	{....},
        {....},
        {....},
        {....},
    ]
}
```

`listId`はサーバー・ローカルいずれもUUIDで生成しており、動的なパスパラメータにも使用しています。

LocalStorageのデータはJotaiの`atomWithStorage`によって、ステートとして参照しています。`atomWithStorage`では`getOnInit: true` を設定しているため、LocalStorageに既存データがあればそれがステートの初期値に使用されます。

つまりテスト実行時に`evaluate`で`{ listId: "リストID", items: [ {...} ] }`を投入すれば、ページへアクセスしたら`items`の値が表示されるはずです。しかし実際には、ランダムな頻度で一覧画面が表示できずにテストが失敗していました。

根本的な原因は、リストIDを生成するEffectがテストと競合していたことでした。エフェクトというのが以下のようなものです。

- `atomWithStorage`が初期値として`{ listId: "", items: [] }`をセットする。
- `useEffect`による非同期エフェクトが実行される。
    - `listId`が未生成の場合、UUIDが生成される。
    - 初期値が`{ listId: "生成されたUUID", items: [] }`で上書きされる。

このような処理がどの程度で完了するかは、実行のたびにばらつきが生じます。

つまり仮想ブラウザでページを読み込んだ際のパフォーマンス次第で、「Playwrightの`evaluate`によって初期値が上書きされる場合」と「`evaluate`でセットした値がエフェクトによって上書きされる場合」のいずれも起こりうる状態になっていました。

テストが成功したのは、非同期エフェクトが`evaluate`でテストデータをセットするタイミングよりもたまたま早く完了したからでした。

### 解決策：`addInitScript`

Playwrightには、ページの読み込みが完了する前に任意のスクリプトを実行するAPI`addInitScript`があります。そのページで使用される本来のJavaScriptが読み込まれるよりも前に、なんらかの前処理を行うことができます。

https://playwright.dev/docs/api/class-page#page-add-init-script

これを使用して、ページへのアクセスよりも先にLocalStorageへ値を入れ込むように修正しました。

```typescript
await page.addInitScript((data) => {
    localStorage.setItem("key", JSON.stringify(data));
}, seedData);

await page.goto("/");
```

この実装によって、ページにアクセスした時点ですでにデータが存在している状態にすることができました。「`listId`が未生成の場合」という条件にも該当しなくなるため、非同期エフェクトもスキップされます。

不自然なリロードも上書きの競合も発生せず、安定してテストできるようになりました。

## DB操作の安定化

今回のアプリケーションでは、データベースに[Turso](https://turso.tech/)を使用しています。Tursoで利用できるのがSQLite互換のlibSQLであることから、ローカルではSQLiteで開発用・テスト用に一つずつ`.db`ファイルを作成しています。

DBを操作するテストケースにおいて、テスト用DBへの書き込みが失敗する問題が起こっていました。

### 問題：SQLiteへの読み書きが競合した

エラーには`SQLITE_BUSY: database is locked`と表示されており、これはDBへ書き込みをしようとしたらロックがかかっていて失敗したことを示しています。

Playwrightの設定は`{ workers: 1, fullyParallel: false }`になっていました。つまり、テストファイル単位・ファイル内のテストケース単位においても全て直列で実行されるということです。それでもDB書き込みがプロセス間で競合していました。

Claudeで原因を探ったところ、テストランナーとNext.jsサーバーの2プロセスが同時にDBアクセスをしている可能性が指摘されました。例えばNext.jsの`<Link>`コンポーネントがプリフェッチを行うなどの理由でリクエストしている最中、次のテストの`beforeEach`がDBリセットのために`DELETE`文を発行するといったケースです。

この場合は、Next.jsからのリクエストがDBをロックしているためPlaywrightからのクエリ発行が成功しません。

いつどこでどのように干渉するかはタイミング次第と思われ、これについてもフレイキネスの要因と思われました。

### 解決策：SQLiteのWALモードを有効化

DBのクライアント生成に、以下のような行を追加しました。

```diff typescript
export const db = drizzle(client, { schema });

+ await db.run(sql\`PRAGMA journal\_mode=WAL\`);
```

WALモードを有効化することで、同時に発生した読み取りと書き込みが干渉しなくなります。

これについてはリモートのTurso自体がWALの拡張版のような機能を有していることもあって、環境差異を減らす観点でも最初から行っておくべき設定だったとも感じます。

## プロセスの明示的なKill

LocalStorageを使用するゲストユーザーのケースとは別に、データベースを使うログインユーザーのケースでも「一覧画面が表示されない」などのトラブルが発生しました。

テストの前処理により、テスト用DBにはデータがきちんと入っています。よって参照できない原因はシーディング以外にあるということでした。

### 問題①：dotenv-cliのコマンドを参照できない

Playwrightでの実行時、Next.jsは`npm run start`で起動します。つまりデフォルトでは`.env`か`.env.local`を参照することになります。

テスト用DBの接続情報は`env.test`に記載しているため、テスト実行時には明確にこちらの参照を指定する必要がありました。しかしそのために必要な`dotenv-cli`のコマンドが参照できていなかったため、アプリケーションは開発時と同様に開発用DBを参照してしまっていました。

前処理で投入したデータはテスト用DBの方にあるため、想定通りのデータ取得ができずに失敗していました。

### 問題②：失敗時のプロセスが再利用される

上記の問題を解決してもテストが失敗します。これはPlaywrightが前回実行した際に起動したポート`3001`番のプロセスが、なぜか生き残っていたためでした。

Playwrightは起動時に同じポート番号のプロセスが見つかった場合、それを再利用します。そのため環境変数の参照は修正されないままでした。

### 解決策：プロセスを明示的に終了した

```bash
npx kill-port 3001 || true && npx playwright test
```

## 3. 壊れにくいセレクタと遷移フローの設計

- **課題**: 文言の重複や、特定の遷移パス（直接アクセス）による404エラー。
- **解決策**:
    - `getByRole` と正規表現（`.first()` 等）を活用し、曖昧なセレクタを排除。
    - 未認証ユーザーのテストでは「ホームからメニュー経由で遷移」という手順を徹底し、アプリの内部状態（LocalStorageの読み込み等）を確実にする。

## 4. 非機能要件への挑戦：ネットワークスロットリングとフレイキー問題

- **テストの構造化**: `/tests/e2e/pages/{path}` 配下に `/functional`（機能要件）と `/non-functional`（非機能要件）を分離して格納。
- **検証内容**: Chromiumのネットワークスロットリング機能を使い、低速環境下で「n秒以内に特定の要素がインタラクティブになるか」といったSLA的な検証を実施。
- **現在の課題（Flaky）**: 
    - 低速環境のシミュレーションは、実行環境（CI等）の負荷に左右されやすく、最もフレイキーになりやすい。
    - 「リトライを許容すべきか、それともアプリの改善（LCP/TBTの最適化）を追求すべきか」という、テストの厳格さと開発効率のトレードオフに直面中。

## 5. 今後の展望：CIの高速化（未解決の課題）

- テスト数が増えるにつれ、実行時間の増大が懸念される。
- GitHub Actionsでの **Sharding（テスト分割）** や、プロジェクトごとにテスト用DBを分離する構成への進化が必要。
