現在、Next.jsでフルスタックなアプリケーションを開発しています。ご多分に漏れずClaude Codeを活用して実装しています。

AIとの協業においても、自動テストは重要です。テストコードの実装とはプロダクトコードの設計作業でもあり、動作する要件定義書の作成でもあるためです。「テストをグリーンにする」という指標は、ほとんどの場合で自然言語のプロンプトよりも機械的で確実です。

今回のアプリケーションでは、初期段階からVitestによるバックエンドのテストを実装していました。しかしフロントエンドについては自分自身に自動テストの知見がなく、Storybookを使用するなどして手動で動作確認しながら先延ばしにしていました。

## フロントエンドのテストはどうしたらいい？

Jestは数年前に少し使ったことがありましたが、モダンフロントエンドのテストについては何も知りませんでした。正直な気持ちで言えば「JestとかReact Testing LibraryとかCypressとか色々あるけど、何をどう組み合わせたらいいかよくわからない」という感じです。

調査した結果、2026年現在は実ブラウザエンジン上でテストを実行するテスティングフレームワークが最適と判断しました。そこで採用したのがPlaywrightです。

## なぜPlaywright（E2Eテスト）だったのか

### テスト戦略との適合

テストサイズという概念があります。

自動テストの分類手法であり、スコープというよりは実行範囲で定義しているものです。
こちらの記事や講演でわかりやすく説明されています。

https://gihyo.jp/dev/serial/01/savanna-letter/0003

https://www.youtube.com/watch?v=C0zNc4bdWhY

定義としては以下のとおりです。

| サイズ | 定義 |
| --- | --- |
| Small | 単一プロセスで実行 |
| Medium | 単一マシンで実行 |
| Large | 外部API等も含め制限なし |

今回は以下の理由からMediumサイズを主軸に据えて実装しています。

- 自動テストがないプロダクトに後から実装する上で最適なサイズであること。
- 設計変更やリファクタリングがしやすいこと。

実装コストの観点ではSmallテストが一番始めやすいのですが、Smallには実装との距離が近いという特徴があります。Smallテストは単一のプロセスで実行するという定義上、いわゆる「ユニットテスト」と聞いてイメージするものに近いテストになります。

大きな変更が頻繁に起こりうる状況では、そういった実装との距離が近いテストはすぐに動かなくなってしまいやすいです。開発を支えてくれるテストを育てていく段階において、Smallテストに投資するのはやや非効率です。

Smallテストは、現状を肯定してもよい場面において最も効果を発揮します。これからもどんどん変更を加えていく段階においては、リファクタリングやリアーキテクティングの支えになってくれるスコープの広いテストの方がコスパがいいのです。

そのような考えのもと、今後しばらくはMediumサイズのテストを重点的に実装するという方針が最初から定まっていました。

バックエンドに対してはServer Actionsを起点とするテストを実装し、最終的な戻り値＋データベースの状態を検証しています。フロントエンドにおいては、PlaywrightによるE2Eテストが方針に適合すると考えました。

### 実際のブラウザに近い環境でテストできる

Playwrightは、実際のブラウザエンジンでレンダリングをした上でアプリケーションを動かすことができます。

ReactフロントエンドをテストするツールとしてはReact Testing Library（RTL）の存在も知っていましたが、RTLはブラウザAPIの代替実装である`jsdom`を実行基盤とします。
実際のブラウザとは環境差異が生じる懸念があり、特にReactの`useOptimistic`等のモダンなAPIを使用したUIが動作するか不安でした。

さらに今回は新規開発であるため、しばらくは機能追加・仕様変更・スタイル修正が活発に行われることが前提です。

コンポーネント単位などの詳細に踏み込んだテストには`jsdom`ベースのライブラリも適合するかもしれませんが、少しの変更で通らなくなるテストを増やしてもUI変更のコストが上がるばかりでメリットは多くありません。

Mediumテストを中心とする戦略もあり、アプリケーションの細部よりは動作（ふるまい）を広範的にテストできる手法の方が望ましいと考えPlaywrightの採用に至りました。

### 備考：Cypressとの比較

近いツールにはCypressもありますが、こちらはあまり比較検討の対象にはしませんでした。

2026年現在ではPlaywrightの方が勢いがある印象が強く、実際にnpmのダウンロード数でも上回っています。

並列実行やWebKitエンジンにもデフォルトで対応しているなど、機能面での優位性もあります。

### 備考：Vitest Browser Modeの検討

Vitest Browser Modeについては、選定の段階では明確に調査・比較していませんでした。存在を知った1年以上前は実験的な機能であり、まだ導入できる段階ではないという印象のまま忘れていたからです。

ただ現時点で改めて調査してみると、Browser ModeはE2Eテストよりはコンポーネント単体を実ブラウザで動作させるテストに特化しているようでした。どちらかといえばSmallテストを志向しているような印象が強く、今回のテスト戦略にはあまり合致しないと考えています。

## 導入

まずはとりあえず動くテストを追加するべく、Claude Codeに既存機能に対するテストを実装させました。

経験上、E2Eテストのようなスコープの広いテストは環境の構築・メンテナンスがやや難しいイメージがあります。Claudeにより生成されたテストを見ても、実際にVitestのように小さな単位のモジュールをテストするものとは違い、動作しない・動作しても不安定といった傾向がありました。

テストに限らずローカル環境のトラブルシューティングはハマりやすいです。調査・修正には積極的にOpusモデルを使用し、プロダクトコードの実装と並行しながら少しずつ安定させていきました。

構成としてはルートの`/tests`ディレクトリに実装し、以下のように配置しています。

```text
tests/
├── e2e/                   # E2Eテスト（Playwright）のメインディレクトリ
│   ├── globalSetup.ts     # テスト実行前の初期設定（DBマイグレーション等）
│   ├── helpers/           # テストケース間で共有するブラウザ操作等のヘルパー
│   ├── lib/               # テスト用DBクライアントなど、基盤となる共通コード
│   ├── non-functional/    # ネットワークエラーなど、全体に関わる非機能テスト
│   └── pages/             # 画面ごとのテスト
│       └── (各ページ)/
│           ├── functional/     # 機能要件のテスト
│           └── non-functional/ # パフォーマンスなどの非機能テスト
├── helpers/               # Vitest（単体・結合テスト）用の共通ヘルパー
└── migrations/            # テスト実行時に使用するDBマイグレーション
```

## やったこと

### DBを使う機能のテスト

仮想ブラウザの操作からデータベースへの書き込みまでを通したE2Eテストです。Vitestで書いていたサーバーサイドのMediumテストと同じく、テスト前にシーディング、テスト後にクリーンアップという流れで組んでいます。

DBへの参照は、Drizzle ORMのクライアントをE2Eテスト用に切り出した薄いラッパーを介して行います。アプリ側のクライアントは`top-level await`を含む都合でPlaywrightから直接importできなかったため、`tests/e2e/lib/testDb.ts`に別途用意しました。

Playwrightの`globalSetup`では、初回のみマイグレーションとマスターデータの投入を行います。

```ts:tests/e2e/globalSetup.ts
export default async function globalSetup() {
    await db.run(sql`PRAGMA journal_mode=WAL`);
    await migrate(db, { migrationsFolder: "./migrations" });
    await seedDatabase();
}
```

各テストファイルでは`beforeEach`でテーブルをクリーンアップ＋マスターデータを再投入し、`afterEach`でもう一度クリーンアップしています。

```ts
test.describe("テストケース名", () => {
    test.beforeEach(async () => {
        await resetDatabase();
        await seedDatabase();
    });

    test.afterEach(async () => {
        await resetDatabase();
    });

    test("...", async ({ page }) => {
        // ページ操作とアサーション
    });
});
```

テスト本体は、ブラウザ操作（フォーム入力やボタンクリック）と、それによって発生するDB側の状態変化の両方をアサーションの対象にします。サーバーサイドのテストと同じく「同じ入力なら同じ最終状態に至ること」を担保する構成です。

### LocalStorageを使う機能のテスト

今回のアプリには、アカウントを持たないゲストユーザー向けの仕様があります。

未ログイン状態ではデータをサーバーに保存せず、ブラウザのLocalStorageへ永続化することで、登録不要でアプリを試せるようにしています。Jotaiの`atomWithStorage`を使い、LocalStorageとReact側のステートを同期する構成です。

このようなLocalStorage依存の機能をE2Eテストする際は、ページにアクセスするより前にLocalStorageへ値を入れておきたくなります。このようなシーディングにはPlaywrightの`addInitScript`を使用しました。

https://playwright.dev/docs/api/class-page#page-add-init-script

このAPIではページのJavaScriptが評価されるよりも前に任意のスクリプトを実行できるため、ページアクセス時点ですでにデータが存在する状態を作れます。

```ts
await page.addInitScript((data) => {
    localStorage.setItem("key", JSON.stringify(data));
}, seedData);

await page.goto("/");
```

### 外部サービスに依存した機能のテスト

今回のアプリケーションでは、パスワードレス認証のために6桁のログインコードをメール送信する機能があり、メール送信には[Resend](https://resend.com/)を使っています。

E2Eテストで悩むのが、外部のSaaSや課金枠を消費するサービスに依存した機能の扱いです。実物のサービスへリクエストを飛ばす場合はスコープがネットワーク外部へ及ぶため、テストサイズで表すと「Large」になります。

Largeテストには次のような問題があります。

- 外部サービスのレート制限・ネットワーク状況に左右されて実行が安定しない
- 通信のオーバーヘッドがあるため実行時間が長い

テストサイズは、依存対象をモックへ差し替えることによって下げることができます。

今回はResendを置き換えるフェイク実装として[`resend-local`](https://www.npmjs.com/package/resend-local)というOSSを採用しました。Resendと同じAPI仕様を持つローカルサーバーです。

Playwrightの`webServer`で、Next.jsの起動と並行して`resend-local`を立ち上げています。

```ts:playwright.config.ts
webServer: [
    {
        command: "npx resend-local --port 8005",
        url: "http://localhost:8005",
        reuseExistingServer: !process.env.CI,
    },
    {
        command: "npx dotenv-cli -e .env.test -- npm run start -- -p 3001",
        // ...
    },
],
```

テスト側では、`resend-local`が提供するREST APIをポーリングして送信済みメールを取得し、本文から6桁のコードを抜き出してログインフォームへ入力する、というヘルパーを書いています。

```ts:tests/e2e/helpers/resendLocal.ts
export async function extractLoginCode(toEmail: string): Promise<string> {
    // resend-local のメール一覧APIをポーリングして
    // 宛先メールアドレスに一致する最新メールから6桁コードを抽出する
}
```

### パフォーマンスのテスト

Playwrightは、Chromium DevTools Protocol（CDP）を介してネットワークスロットリングを設定できます。これを使うと、低速ネットワーク下での読み込み速度やUIの反応速度を、機能テストと同じ仕組みの中で検証できます。

今回のアプリでは、3G相当のネットワーク条件をエミュレートしたうえで「初期表示で優先したい要素が一定時間内に表示される」「ユーザー操作に対してUIが即座にフィードバックを返す」といった項目をテストしています。

```ts
const THROTTLING_3G = {
    offline: false,
    downloadThroughput: 750_000,
    uploadThroughput: 250_000,
    latency: 100,
} as const;

const cdpSession = await context.newCDPSession(page);
await cdpSession.send("Network.emulateNetworkConditions", THROTTLING_3G);
await page.goto("/", { waitUntil: "domcontentloaded" });
await expect(page.locator('textarea[name="value"]')).toBeVisible({
    timeout: 2000,
});
```

このようなテストを書くと、コードベース上で「初期表示において、どの要素を最優先で見せるべきか」が言語化された状態で残ります。新たにコンポーネントを追加するときも、この優先度を踏まえて読み込みタイミングや遅延ロードの方針を決められるようになり、UI設計の指針として機能します。

## 困ったこと

### LocalStorageの初期データ投入がフレイキーになる

ゲストユーザー向け機能のテストが、一部成功したり失敗したりするフレイキーな状態になっていました。

具体的にはLocalStorageへシードデータを投入したうえで行う一覧画面のテストにおいて、入っているはずのデータが参照できない問題が発生していました。

修正前の実装が以下のとおりです。

```ts
await page.goto("/");

await page.evaluate(() => {
    localStorage.setItem("key", JSON.stringify(seedData));
});

await page.reload();
```

一度ページへアクセスしたあとに`page.evaluate`でLocalStorageへ書き込み、リロードして再描画するという手順です。

**原因**: 

アプリ側でもLocalStorageの初期化処理が走っており、これと競合していました。

リロード時にハイドレーションが行われる際、完了するタイミングは毎回異なります。失敗するケースでは、`evaluate`で投入したデータがあとからアプリ側の初期化エフェクトによって上書きされてしまっていました。

**解決策**: 

`page.addInitScript`を使う実装へ修正。ページのJavaScriptが評価されるよりも前にLocalStorageへ値を入れるように変更し、アクセス時にはすでにデータが存在するようにしました。

```ts
await page.addInitScript((data) => {
    localStorage.setItem("key", JSON.stringify(data));
}, seedData);

await page.goto("/");
```

### SQLiteへの書き込みがロックで失敗する

データベースには[Turso](https://turso.tech/)を使用しており、ローカルではTursoと互換性のあるSQLiteの`.db`ファイルを開発用・テスト用に分けて運用しています。

このテスト用DBを操作するテストケースで、事前のシーディングに失敗してテストが動かなくなるケースが発生しました。Playwrightは`{ workers: 1, fullyParallel: false }`で直列実行しているのですが、書き込みが`SQLITE_BUSY: database is locked`というエラーで失敗します。

**原因**:

ブラウザ操作が終わり、Playwright側のアサーションが通って「テストが成功した」と見なされても、Next.jsサーバー側のDBアクセスが完了しているとは限りません。

具体的には、テストランナーが`afterEach` / `beforeEach`でリセット用の`DELETE`を発行したタイミングで、サーバー側ではまだ前のテストに紐づくDBクエリ（例えば`<Link>`のプリフェッチによる読み取り）が進行中という状態になっている可能性があります。

この場合、両者がSQLiteのロックを取り合ってしまい`SQLITE_BUSY`で失敗します。

**解決策**:

DBクライアントの生成時に、SQLiteのWALモードを有効化するようにしました。

```diff ts
export const db = drizzle(client, { schema });

+ await db.run(sql`PRAGMA journal_mode=WAL`);
```

これにより、同時に発生した読み取りと書き込みが干渉しなくなります。そもそもリモートのTurso自体がWALの拡張版のような機能を持っていることもあり、環境差異を減らす観点でも最初から入れておくべき設定だったと感じています。

### テストが開発用DBを参照してしまう

ログインユーザーのテストでも、「一覧画面にデータが表示されない」という問題が発生しました。テストの前処理ではテスト用DBへのシーディングが成功しているため、問題は参照側にあるようでした。

**原因**:

テスト用の環境変数`.env.test`をPlaywrightへ読み込ませる設定が不足していました。

この場合、Next.jsはテスト用の`.env.test`ではなく開発用の`.env.local`を読み込み、開発用DBの方と接続します。シーディングしているのはテスト用DBの方なので、期待通りのデータが読み取れずに失敗していたのでした。

**解決策**:

`playwright.config.ts`の`webServer.command`に`dotenv-cli`を噛ませ`.env.test`を読ませる指定を入れたところ、設定上は正しい状態になりました。

しかし症状はそのままで、テストは引き続き失敗しました。これは、設定が不足した状態で実行した際に起動したポート`3001`のプロセスがなぜか生き残っていたためです。Playwrightは`webServer.url`に応答するプロセスが既にあるとそれを使い回すため、修正後の起動コマンドが反映されない状態になっていました。

該当ポートのプロセスを明示的に終了することで、正常にテストが動作するようになりました。

```bash
npx kill-port 3001 || true && npx playwright test
```

## 今後やりたいこと

### CIへの組み込みと並列化

現状、E2Eテストはローカルでのみ実行しています。VitestによるバックエンドのMediumテストは既にCIに乗せているので、E2Eテストも同じようにCI上で走らせて、PRごとに品質を担保したいと考えています。

ただ現在は`{ workers: 1, fullyParallel: false }`で全テストを直列実行しているため、テスト数が増えるとCIの実行時間がそのまま線形に伸びていきます。CIに乗せるタイミングで並列化は必須だと考えています。

並列実行に踏み込む際に検討が必要なのが、テスト用DBの扱いです。現在は単一のSQLiteファイルを共有しており、`beforeEach`での`DELETE`によるクリーンアップ＋シーディングという形で独立性を担保しています。このまま並列化することはできません。

Playwright公式ドキュメントのExampleのように、Playwrightのシャーディングと`matrix`での並列実行を組み合わせる方法を調査しています。

https://playwright.dev/docs/test-sharding#github-actions-example

### パフォーマンステストのフレイキネス対策

ネットワークスロットリングを使ったパフォーマンステストは、性質上どうしても実行環境の負荷に左右され、フレイキーになりがちです。特にCIに乗せた場合、ローカルよりも環境の揺らぎが大きくなるため、より顕在化することが予想されます。

リトライで吸収するのは安易ですし、テストの意義（一定品質を担保していることを示す）を損ないかねません。タイムアウト値を「致命的な遅延だけを検出するライン」に設定し直す、計測対象を絶対時間ではなく相対値（ベースラインとの差分）に変える、といった対策を検討していきたいところです。

## おわりに

可能な限り安定したE2Eテストを用意することで、手動でのデバッグが削減されました。機能の追加や仕様変更のたびに全機能に対して網羅的な動作確認ができるようになり、期待する振る舞いの確認がしやすくなったのは大きなメリットです。

一方で、特にAIとの相性面には課題が残っています。

Vitestのようなテストランナーと比べると、仮想ブラウザを立ち上げて行うE2Eテストは実行時間が長くなります。AIエージェントを用いた実装において「実装→テストで動作確認→修正」のサイクルで作業させていると、実行時間の長さがネックになってきます。

また、AIエージェントがE2Eテストの実装に消極的になっているような印象も受けます。

Vitestでテストするバックエンドであれば、「TDDで開発」という指示に従ってテストを書いて落ちるのを確認してから実装してくれます。しかしE2Eテストを先に実装させる手順を命じても、なぜかテストの実装を省略していきなりUIの実装に着手することが多々ありました。

実行の効率やハーネスエンジニアリングの観点からも、引き続き改善が必要だと感じています。
